# P0-V2 优化结果（2026-09-29）：脏区分块转换 + 增量 patch 游标

环境：Windows 10，release，gpui-pre 0.3.7（DirectX 图集），窗口 1280x800，画布 3840x2160，300 帧，3 次运行。

## 改动
1. 根因之一：acquire_patch 每帧传 cursor=None，引擎每次返回 reset=true 且脏区为整幅 4K；改为回传上一帧 patch 的 revision 游标后，得到真正的增量脏区。
2. gpui 图集以 ImageId 为键、只在首次插入时上传，无局部更新 API；改为 256px 分块，每块独立 RenderImage，仅脏块重转 BGRA 并换新 ImageId，旧块用 cx.drop_image 释放（原实现从不 drop，会泄漏图集）。

## 基线（优化前）
平均 19.5 fps，最低瞬时 5.75 fps。

## 仅做分块、游标仍为 None（脏区恒为全屏，135 块/帧）
平均 22.4-26.3 fps，最低 9-13 fps，P99 约 60-72 ms。结论：单靠分块无效，全屏脏区下反而略有开销。

## 结论
- 含首帧：平均约 58.6-59.4 fps；首帧约 70-80 ms（整幅 4K 一次性光栅化+上传，属启动预热）。
- 稳态：平均 59.4-60.0 fps（已贴近 60Hz vsync 上限），P99 约 20-30 ms，最低 28-48 fps，>20ms 的帧 2-11 帧/300。
- 按 spike 原判据（最低瞬时 >= 55fps）仍标未通过；按平均帧率已达标。残余长尾疑似 D3D 上传/系统调度抖动，运行间波动大（第 3 次明显更差）。
- 局限：脏区随箭头变长增大（末段约 2400x600 px），本测试为单箭头；draw_arrow 未按脏区裁剪；仅测了 256px 分块，未试其他块大小。
- 下一步建议：给 draw_arrow 加脏区裁剪；试 512/128 块大小；定义判据为 P99 而非最低瞬时；如仍要压长尾再考虑 rayon。无需 Vello。

## 第三轮（2026-09-29）：修复 Mask 负优化 + 128 档"不结束"排查 + 长尾归因
**测量条件（重要）**：同期有后台 C++ 编译及多个高 CPU 的 `find` 进程占用 CPU/磁盘，数据偏悲观，且运行间波动大（个别运行整体掉到 24-38 fps，已如实保留在范围里）。因此每个配置多次运行取范围，并用旧实现（`SPIKE_MASK=full`）与新实现交替运行作对照。release，4K，300 帧，稳态=剔除首帧。

### 1. Mask 负优化修复
- 查 tiny-skia 0.11.4 源码：`Mask` 为 1 字节/像素 Alpha 蒙版，提供 `data_mut()` 可直接读写；`Mask::clear()` 是整块 fill(0)（约 8MB/帧），`fill_path` 走完整光栅化路径。
- 改法（`SPIKE_MASK=dirty`，默认）：Mask 常驻全 0；每帧只把脏区整数外扩矩形的行置 255，画完只把这些行复位为 0；清除脏区也用同一整数矩形，边缘不再半清半画。旧做法保留为 `SPIKE_MASK=full` 作对照，`none`（无 Mask，仅包围盒跳过）仅作性能参考。
- 正确性：三种模式、两种块大小、全部运行的最终画布 FNV 校验和一致（`7f2c361deb0f2325`）。
- 结果（交替运行，256 档 8 次；128 档 5 次）：

| 块 | 模式 | 次数 | 稳态平均fps | 稳态 P50 ms | 稳态 P99 ms | 稳态最大 ms | >20ms 帧数 | 光栅化 ms | 合成 ms |
|---|---|---|---|---|---|---|---|---|---|
| 256 | full(旧) | 8 | 59.46-60.05 | 16.65-16.69 | 19.08-32.36 | 19.30-34.11 | 0-3 | 1.41-1.46 | 1.38-1.54 |
| 256 | **dirty(新)** | 8 | 59.56-60.04 | 16.65-16.69 | 18.87-20.19 | 19.37-34.64 | 0-3 | **0.47-0.61** | 1.41-1.66 |

结论：光栅化耗时由约 1.4-1.5 ms 降回 0.47-0.60 ms（约 -60%），负优化已消除，回到第一轮水平。帧率/P99 上，旧新版本的范围大幅重叠，差异在噪声内，不能声称帧间隔有改善（帧间隔本就不受这 ~1ms CPU 影响，见第 3 节）。稳态 P50 恒为 16.6-16.7 ms（vsync 上限）。

### 2. 128 档"运行 >120s 不结束"排查
- 结论：**不是 128 档特有的 bug，不是死循环/块数暴涨/O(n²)**。128 档每帧重建块数最大 133，render 耗时最大约 6-9 ms，drop_image 无累积；帧循环由 300 帧计数强制结束。
- 证据：给程序加了阶段时间戳与看门狗（3 秒无新帧则告警）。系统安静时，128/256/512 三档总墙钟都是约 6.1-6.5 s（启动到 main 约 0.2 s、open_window 约 0.5 s、300 帧约 5.0 s、退出约 0.5 s），与块大小无关。
- 慢的部分在"帧循环之外"：使用刚复制出来的新 exe（首次运行）且系统繁忙时，观测到总墙钟 112 s（无阶段日志）、27 s、31 s；有阶段日志的两次显示：启动到 main 1.8-2.3 s、`open_window` 4-11 s、退出 5-18 s，帧循环本身仍只有 7-8 s。20 个自旋进程加压下再跑 128 档 3 次，墙钟 8-9 s，也未复现。
- 判断：>120s 是"新 exe 首次运行 + 后台高负载"导致的进程启动/窗口创建（D3D 设备初始化）/退出变慢，帧循环并未卡住。**这是推断，112 s 那次缺阶段日志，原始 >120s 未能直接复现**，没有代码 bug 可修。已保留阶段日志与看门狗（stderr），下次再现可直接定位。修后 128 档 12+ 次均正常跑完。

### 3. 长尾来源探查
- 插桩：每帧记录 render 总耗时（光栅+合成+构建元素树）、帧间隔、脏区像素数、重建块数；报告中对每个 >20ms 的帧输出"前一帧 render 耗时"和"非 render 时间"（帧间隔 = 前一帧 render + 呈现/等 vsync/调度时间）。
- 数据（上述 256/128 共 68 次运行中出现的 53 个 >20ms 长尾帧）：这些帧的**前一帧 render 耗时最大仅 5.55 ms，无一超过 8 ms**；其"非 render 时间"为 15.1-33.1 ms（中位 18.7 ms）。同时所有运行里 render 耗时的最大值（约 4.7-8.7 ms）出现的帧并没有变成长尾帧。
- 结论：>20 ms 的帧间隔**不对应 CPU 侧合成/转换耗时尖峰**，而是出在 render 之外——呈现/上传/vsync 调度或系统抢占（帧间隔多呈 ~33/50 ms，即错过 1-2 个 vsync）。在当前后台高负载下这一现象更明显。本轮未进一步区分是 D3D 上传还是操作系统调度，需要 GPU 侧计时（如 PIX/ETW）才能继续，不在 spike 范围内。
- 反推：继续优化 CPU 侧（rayon 等）对长尾无帮助；长尾需在系统安静时复测确认有多少是后台负载造成的。

### 本轮小结
- 稳态平均 fps 约 59.4-60.1（贴近 60Hz 上限），P50 16.6-16.7 ms，P99 18.9-20.2 ms（dirty 模式，多数运行；个别受干扰运行 P99 可到 30+ ms），稳态最大帧间隔 19.4-35.4 ms，>20ms 帧 0-3 帧/300。
- 按原判据（最低瞬时 >= 55fps）仍不稳定通过；按 P99≈20ms 与平均 60fps 看已基本达标。因后台负载偏悲观，建议在后台任务结束后重跑一轮定稿。
- 改动文件：仅 `src/main.rs`（新增 `SPIKE_MASK` 环境变量、脏区行级 Mask、插桩、阶段日志、看门狗）与本文档。
