# 语音转文字冷启动：UI 退出后怎么不丢开头

> 状态：调研 + 本机离线实测完成，**未改任何产品代码**；方案待用户拍板。日期 2026-10-13。依据 [`principles.md`](../principles.md) 的优先级链（高性能 > 低内存 > 高 fps > 少编译依赖 > 多用系统能力，另含不常驻）。
> 关联：[`design/tray-host-split.md`](../design/tray-host-split.md)（§10 第 4 条已于 2026-10-13 改判为"绑了语音热键也立即退出"，其中写了"后续可能另做 worker 预拉优化"，本文就是这件事的调研；UI 冷启动分段见其 §12.1）、[`guides/snow-stt-worker.md`](../guides/snow-stt-worker.md)（worker 协议与生命周期）、[`research/stt-model-selection.md`](stt-model-selection.md)（模型加载耗时的历史口径）、[`research/tray-host-minimal.md`](tray-host-minimal.md)（宿主内存与导入表约束）。
> 资料来源说明：产品行为全部来自读代码和本机实测（探针与脚本在 scratchpad，不入仓库）。业界做法先走网络搜索，再对能打开的页面 WebFetch 核对；只有搜索摘要、没能读到正文的写"未证实"。
> 任务背景里写的"现行规则：绑了语音热键 UI 保活"已经过时：`accdbdcf`（2026-10-13 12:38）已改判为不保活，`host_spec::keep_alive_reasons` 只剩 MCP 与 OCR 预热。所以本文的问题是改判之后遗留的那一条：冷拉起 UI 时按住说话的开头会丢多少，能不能不丢。

## 1. 结论（先看这里）

1. **"开头丢约 1s"这个估计偏乐观，丢的主要不是 UI 冷启动。** 现行 worker 的顺序是：收到 START → **加载模型 → 才打开麦克风**（`snow-stt/src/main.rs` 注释写明"避免把加载期间的旧音频喂进去"）。所以从按键到"开始听"之间说的话**全部丢掉**，这段时间 = UI 冷拉起 + worker 启动 + **模型加载** + **麦克风打开**。本机实测（n=3，机器当时有 Lark、浏览器等后台负载）：默认双语流式模型 x-asr 480ms 加载 5.7 / 9.4 / 13.6 s，较小的 multi-zh-hans 3.3 / 3.8 / 4.2 s；麦克风打开（WASAPI `Initialize` 到首包）0.7~0.9 s（两次离群 1.3~1.5 s，都是某个进程里的第一次打开）。UI 冷拉起到能起 worker 只占 0.3~0.5 s（估算）。
2. **这和 UI 退不退无关。** UI 常驻时同样要加载模型再开麦，丢的时间只少 0.3~0.5 s（占总量的 3%~10%）。也就是说"UI 保活"这条规则从来没有真正保护住开头；它保护的只是那 0.3~0.5 s。旧规则的前提（丢约 1s）和本机数据不符。
3. **真正的修法在 worker：先开麦、边录边存（环形缓存）、模型加载完再把积压音频快进喂给识别器。** 这样丢的只剩"按键到麦克风可用"那一段（≈1~1.4 s 冷 UI，其中 0.7~0.9 s 是麦克风硬件/驱动打开本身，所有方案都躲不掉），模型加载时间不再丢字，只会让字晚出来。积压追赶很快：流式 RTF 本机实测 0.06~0.21，3~13 s 的积压追赶 0.2~2.7 s。
4. **推荐的落地顺序**：①worker 先开麦 + 环形缓存 + 追赶（唯一"必须做"，不动宿主）；②UI 进程一进 `main` 就并行拉 worker（宿主给启动参数加一个提示，不增加宿主依赖）；③宿主直接拉 worker 只在实测证明②的剩余差距听得出来时再做（预计只再省 0.06~0.15 s）。**宿主自己录音（WASAPI）不建议**：比③只再快 ~0.1 s，却要给宿主加 `ole32` 导入和 13 个运行时模块、跨进程交接 PCM（§4.2）。
5. **想要零丢失只有一条路：麦克风常开**（Handy 的 "Always-On Microphone" 就是这个思路），与"不常驻"和隐私指示灯冲突，不推荐，列为用户可选的决定点（§9）。
6. **§10 第 4 条**的"代价"一句要改写：把"开头可能丢约 1s"换成"丢的是按键到麦克风可用的约 1~1.4 s，模型加载不丢字"，并把"worker 先开麦缓存"登记为这条的配套工作（§8）。

## 2. 现状：从按下热键到"在听"

读代码得到的流程（`dictation/engine.rs`、`client.rs`、`tools/snow-stt/src/{main,session,source}.rs`、宿主 `queue.rs` / `machine/tests.rs`）：

```
按下 F10
  → 宿主 WM_HOTKEY，命令入队（按住说话的按下/松开保序），CreateProcess 拉 UI
  → UI 冷启动 → 会话握手 → 收到 start_dictation / toggle_dictation
  → UI 拉 snow-stt（等 READY）→ 发 START，紧跟 PING
  → worker：加载模型（几秒）→ 才 MicSource::open（麦克风）→ 进入主循环 → 回 PONG
  → UI 收到 PONG 才算"在听"（此前浮窗/托盘显示"加载中"）
```

三个后果：

- 按键到 PONG 之间说的话**一个字都没进过任何缓冲区**（麦克风还没开）。
- 按住说话松开得比 PONG 早：引擎直接结束进程，**整段话丢弃**（`snow-stt-worker.md`「进程生命周期」第 3 条："还没开始听就要结束，没有可冲刷的音频，直接结束进程"）。模型加载 4~14 s 时，短句几乎必丢。
- 切换式（用户配的 F10 是 `dictation_toggle`）同理：第二次按键前若还在加载，同样是"加载中"，说的话没录下来。

## 3. 实测数据（2026-10-13，本机）

环境：Dell，i5-13500，32GB，Win10 19045，release 构建的 `build\stt\release\snow-stt.exe`（2026-10-09 构建），模型取用户数据目录里已装的（只读，没写任何数据目录）。深信服 SNAC 注入每个进程（见 `tray-host-split.md` §12.8），数字都含它。**测量时机器有后台负载**（CPU 约 23%：Lark、浏览器等），所以加载与 RTF 比 `stt-model-selection.md` 的历史数据慢约 2 倍；用户日常使用时同样有这类负载，所以不当作"测坏了"，但具体数字看量级，不看小数。每个实验 n=3，脚本 `<scratchpad>/sttbench.ps1`。

### 3.1 worker 进程启动与模型加载

| 项 | 实测（3 次） | 备注 |
| --- | --- | --- |
| `CreateProcess` 调用本身 | 14~55 ms | 脚本里 .NET `Process.Start`，含 SNAC 钩子 |
| 进程启动到 `READY` | 74 / 97 / 77 ms（无 START）；带 START 的十余次里 72~202 ms | worker 此时只读 stdin，不碰模型与麦克风 |
| x-asr 480ms（默认双语流式，169MB）`load_ms` | **5747 / 9427 / 13585 ms** | 历史评测 2549 ms；`--wav` 口径，`stats:` 行 |
| multi-zh-hans-2023-12-12（76MB）`load_ms` | **3256 / 3826 / 4233 ms** | 历史评测 1873 ms |
| START → `PONG`（现行流程，真麦克风）x-asr 480ms | 6.8 / 11.6 / 14.4 s | 比 `load_ms` 多的部分 = 打开麦克风 + 起主循环 |
| START → `PONG` multi-zh | 3.8 / 4.2 / 4.6 s | 同上；与 wav 口径的差约 0.4 s，但受加载抖动影响，分不干净 |
| RTF（识别速度） | x-asr 480ms 0.082~0.212；multi-zh 0.060~0.086 | 历史 0.054 / 0.036；本机当时负载高 |
| 听写中的内存（`PrivateMemorySize64` / 工作集） | x-asr 480ms 237~248 / 250~260 MB；multi-zh 137~147 / 152~156 MB | 听写中才有 |
| 空闲 worker（READY 后、未载模型未开麦） | 私有 3.1MB / 工作集 8.8MB | 来自一次 START 失败后仍存活的进程，n=1，只作量级参考 |

模型加载没有任何一次低于 3 s，同一模型三次之间差 2~2.5 倍（x-asr 480ms 真麦克风三次 6.8 / 11.6 / 14.4 s，没有单调趋势），原因没查：后台负载与首次读盘（冷页缓存）都有可能，**未证实**。

### 3.2 麦克风打开本身要多久

写了一个一次性探针 `<scratchpad>/audioprobe`（`windows` crate，WASAPI 共享模式默认麦克风，进程先做宿主同款加固：扩展点缓解 + `ImmDisableIME(-1)` + 一个隐藏窗口）。

| 配置 | `IAudioClient::Initialize` | 到首个音频包 | n |
| --- | --- | --- | --- |
| 16kHz 单声道 16 位，系统转换（与 `snow-audio-recorder` 同思路） | 1429 / 871 / 849 ms | 1480 / 920 / 894 ms | 3 |
| 混音格式（48kHz 立体声 float），不转换 | 874 / 789 / 747 ms | 913 / 829 / 782 ms | 3 |
| 同进程二次打开（上次释放后 1 s） | 689~725 ms（含枚举） | 705~741 ms | 3 |
| 枚举默认端点 + `Activate` | 每次 ~12~22 ms + ~9~11 ms | — | 全部 |

结论：**麦克风打开 0.7~0.9 s，与采样格式转换无关，二次打开只略快**；瓶颈在设备/驱动/音频引擎（本机默认麦是 Realtek Jack Mic，另有 SNAC），不是代码。两次 1.3~1.5 s 的离群都出现在该进程的第一次打开（第一轮 1.43 s、另一轮 1.29 s）。换机器会不同，**但这个量级说明"按键后马上说话"本来就不可能零丢失**，除非流已经开着（§4.6）。worker 里用的是 `snow-audio-recorder`，它的打开耗时没有单独测（与探针同量级，**未证实**）。

### 3.3 UI 冷拉起到能起 worker

不重测，引用 `tray-host-split.md` §12.1（release，进程创建时间起算，n=6，范围见原表）：UI 进到 `main`/引导完成热 56 ms、冷（清页缓存）145 ms；GPUI 初始化 + 配置加载完成（"进程优先级已设置"）热 249 ms、冷 429 ms。拆分后没有托盘初始化，听写命令在事件循环起来后处理，**估算**热 ≈ 0.28 s、冷 ≈ 0.45 s（派生值，没有对听写单独实测）。宿主侧热键到 `CreateProcess` 返回 ≈ 10~11 ms（`tray-host-minimal.md` §3.6）。

### 3.4 把上面拼起来：按键到"麦克风在录"（现状）

| 情形 | 公式 | 结果 |
| --- | --- | --- |
| 现状，UI 冷拉起，multi-zh | 宿主 0.01 + UI 0.28~0.47 + worker 0.09 + 加载 3.3~4.2 + 开麦 0.8 | **4.5~5.6 s** |

即：旧规则的保活只省 0.3~0.5 s。下面所有方案都是围绕"把加载从这条链里拿掉"。

## 4. 候选方案

记号：`lead` = 按键到"能起 worker 的那个进程开始执行"的时间；`M` = 麦克风打开 0.7~0.9 s；`W` = worker 启动 0.09 s；`L` = 模型加载。除 §4.1 的"先开麦缓存"外，下面每个方案**都要和它搭配**，否则 `L` 还在链里。

### 4.1 worker 先开麦 + 环形缓存 + 追赶（与谁拉起 worker 无关）

START 一到：①立刻开麦（独立线程）并把 16kHz 样本写进有上限的环形缓冲；②同时在另一线程加载模型；③模型就绪后先把缓冲里的积压按块快进喂给识别器（现有 `feed`/`poll` 循环照用，输出照常是 PARTIAL/FINAL），追平后转实时。离线模式（VAD 切句）同理，积压喂 VAD。系统语音后端自己占麦克风、不能喂 PCM，**这条不适用**，它的加载本来就快。

| 项 | 数据 |
| --- | --- |
| 丢字窗口 | 只剩"按键到麦可用"：`lead + W + M` |
| 内存 | 缓冲 16kHz f32 = 64KB/s；上限取 30 s ≈ 1.9MB（i16 减半）。听写中 worker 本来就 140~250MB，可忽略 |
| 追赶耗时 | 积压 ≈ `L` − M。multi-zh 积压约 3 s × RTF 0.06~0.09 ≈ 0.2~0.3 s；x-asr 480ms 积压 5~13 s × RTF 0.08~0.21 ≈ 0.4~2.7 s |
| 字出来的时间 | 晚于说话时间，晚多少 ≈ `L` + 追赶；输出到输入框是"一口气打出来"。需要 UI 在"录音中，识别稍后"时给出提示，而不是"加载中"（现行语义：没 PONG 就没在听） |
| 复杂度 | 中。主循环、`AudioSource` 抽象已有，改动集中在 `main.rs` 的启动顺序与新增一个缓冲来源；协议要加一个"已在录音"事件（旧的 `PONG` 语义是"主循环已开始"，可保留），`engine.rs` 状态机多一个"录音中/加载中"相位。有 Fake 后端与脚本化来源，可做确定性单测 |
| 宿主闭包 / 导入表 | 无影响 |
| 副作用 | 按住说话在"能录音"之后松开，音频不再丢：松开 = STOP，worker 等模型加载完、积压喂完再冲刷（引擎现行"还没开始听直接结束进程"要改成"已在录音则等待"）；`max_seconds` 计时要从开麦算 |

### 4.2 选项 a：宿主收到语音热键就直接拉 worker

| 项 | 数据 / 评估 |
| --- | --- |
| lead | 宿主 `CreateProcess` ≈ 10 ms；按键到"麦在录" ≈ 0.01 + 0.09 + 0.8 ≈ **0.9~1.0 s** |
| 与"UI 起来再拉"相比 | 少 UI 事件循环那段 0.28~0.47 s |
| 宿主内存 / 闭包 | worker 是另一个 exe（`tools/snow-stt`，独立 workspace），不进宿主依赖闭包；宿主只多一次 `CreateProcess`，导入表不变（`kernel32` 已有）。宿主要知道 worker 路径与 START 行：由 UI 在写 `host/spec.json` 时按现有 `prepare_launch` 算好放进快照（宿主不链 snow-config，这点不能变）；快照变陈旧（换模型、卸载模型）要靠 UI 配置变化时重写 |
| 交接给 UI | 难点。worker 的 stdin/stdout 是匿名管道，归宿主。办法一：宿主 `CreatePipe`（缓冲调大到 256KB）再 `DuplicateHandle` 把两端交给 UI，UI 起来后接管读事件；松开事件宿主可直接写 STOP。办法二：worker 新增 `--pipe` 命名管道服务端，UI 起来后连上，积压事件先攒在 worker 里；但松开要等 UI 起来才能送达 STOP，按住说话会多录 0.3~0.5 s 的尾音（可用"STOP 携带宿主的 QPC 时间戳，worker 截掉之后的音频"弥补，QPC 全系统一致） |
| 异常 | UI 起不来（熔断、崩溃）：宿主要杀 worker，否则麦克风一直开着。托盘 tooltip 要提示。前台全屏闸门等"本次其实不该响应"的情形，宿主得在拉 worker 前判断，否则白开了麦 |
| 复杂度 | 高：宿主协议新增字段与消息、句柄交接、孤儿清理、快照校验。宿主是"极小 Win32"，每加一块都要有对应守卫和测试 |
| 收益 | 比 §4.3 再省约 0.06~0.15 s（见下） |

### 4.3 选项 a'（本文新增）：UI 进程一进 `main` 就并行拉 worker

宿主拉起 UI 时，已知队首命令是不是 `start_dictation` / `toggle_dictation`，给 UI 命令行加一个提示参数（如 `--hint dictation`）。UI 在 `main` 最前面（和"启动即并行采集"同一位置，`tray-host-split.md` §6 优化点 1），不等 GPUI 初始化，直接读配置、算 `prepare_launch`、拉 worker；worker 由 UI 直接持有 stdio，**没有句柄交接问题**，宿主不增加任何依赖。

| 项 | 数据 / 评估 |
| --- | --- |
| lead | UI 引导完成热 56 ms / 冷 145 ms（§3.3，p95 冷 236 ms）+ 读配置（未测，轻量）；按键到"麦在录" ≈ 0.01 + 0.06~0.15 + 0.09 + 0.8 ≈ **1.0~1.1 s** |
| 与 a 的差 | 0.06~0.15 s（估算） |
| 宿主影响 | 只多一个启动参数；闭包 / 导入表 / 内存不变 |
| UI 影响 | `main` 里多一条无 GPUI 依赖的早期路径；配置读取要和现有启动顺序协调；之后事件循环收到命令时认领已拉起的 worker（`engine.rs` 接受"已有 worker"） |
| 复杂度 | 中，低于 a |

### 4.4 选项 b：宿主自己用系统 API 先录音，再交给 UI

按 `tray-host-split.md` §1 的边界（"宿主只管能让用户唤起 Cisox 的东西"）和 `workspace-guard` 的导入表闸门评估。

| 项 | 实测 / 评估 |
| --- | --- |
| waveIn（winmm） | **不可行**：`winmm` 在导入表禁止前缀里（`workspace-guard/src/imports.rs` `FORBIDDEN_PREFIXES`） |
| WASAPI | 要 COM：宿主新增 `ole32` 导入（不在白名单 `ALLOWED_EXACT`），或运行时 `LoadLibrary`。探针实测（宿主同款加固下可用，扩展点缓解不影响音频）：启动采集后**新增 13 个模块**（`mmdevapi`、`audioses`、`clbcatq`、`shcore`、`devobj`、`cfgmgr32`、`powrprof`、`umpdc`、`sechost`、`bcrypt`、`bcryptprimitives`、`advapi32`、`kernel.appcore`），**私有提交 +0.5MB（1.34 → 1.83~1.88MB），工作集 +2.7MB（6.61 → 9.34~9.41MB）**；释放采集后基本不回落（1.82~1.87MB，DLL 留在进程里）。基线是"空窗口"，没有托盘与热键，真宿主 2.1~2.2MB 上加约 0.5MB，仍在 ≤6MB 目标内 |
| lead | ≈ 0.01 + 0.8（M）≈ **0.82 s**，比 a 只快 W（0.09 s），比 a' 快约 0.2~0.3 s |
| 数据去向 | 宿主要缓存 PCM（16kHz i16 = 32KB/s，14 s 约 0.45MB；若按设备原生 48kHz 立体声 float 则 384KB/s，必须在宿主里重采样或限时），再经管道交给 worker / UI；宿主要在前台全屏闸门、暂停等判断之后才能开麦；"麦克风在用"指示归属 `snow-shot.exe`，隐私上更难解释 |
| 复杂度 | 高：COM 初始化、设备失效、默认设备切换、权限被拒、重采样、跨进程交接都得在"极小宿主"里重新做一遍（现成实现在 `snow-crates/snow-audio-recorder`，但它不是为宿主闭包设计的，不能直接链） |
| 评价 | 内存代价其实不大，**真正的代价是破坏宿主边界与导入表闸门，换来的只是比 a' 快 0.2~0.3 s**。不建议 |

### 4.5 选项 c：只预拉 worker、不预拉 UI；或 worker 空闲保活

- **c1 预拉 worker 不预拉 UI**：就是 a / a'（worker 单独早起，UI 稍后）。
- **c2 worker 保活、UI 退出**：保活什么？
  - 保活"空进程"（READY 后等 START）：私有 3.1MB / 工作集 8.8MB（n=1），能省的只有 W = 0.09 s，而模型加载与开麦都还在链里。**不值得**。
  - 保活"已加载模型"：私有 **137~248MB**，比常驻 UI 的 135MB（任务背景数字）还大，违背目标（principles：不常驻，高性能优先但"低内存"紧随其后；用户配 F10 却不用语音时纯浪费）。可以做成"空闲 N 秒后卸载"（LocalYapper 的做法，见 §5），但仍是一个常驻 150MB+ 的进程，**不建议默认**，可作用户可选项。

### 4.6 选项 d：麦克风常开 / 预热音频流（零丢失唯一办法）

按键时流已经开着，丢字窗口理论上降到 0。代价：常驻进程（至少 worker 空壳 3MB + 音频引擎）、系统麦克风指示灯常亮（隐私观感）、违背"不常驻"。Handy 把它做成默认关的开关（§5）。**不推荐默认开启**；若用户想要，放在设置里做成显式选项，并且它与"UI 随时退出"互不冲突（流由独立小进程持有）。

## 6. 推荐方案

1. **做 §4.1（worker 先开麦 + 环形缓存 + 追赶）**。这是丢字时间从 4.5~15 s 降到 ~1.2 s 的那一步，与 UI 退不退无关，也与宿主无关。必须同时改：引擎"还没在听就松开"的语义（已在录音则等加载完、喂完积压再冲刷）、UI 的状态提示（"正在录音，识别稍后出字"）、协议加"已在录音"事件。
2. **再做 §4.3（a'）**：宿主给 UI 加 `--hint dictation`，UI 在 `main` 最早处拉 worker。估算再省 0.2~0.3 s，宿主零依赖增量。
3. **§4.2（a）暂不做**：与 a' 只差 0.06~0.15 s，却带句柄交接与孤儿清理。等 §7 实验 E2 显示 a' 的剩余差距在冷页缓存下 > 0.3 s 再复议。
4. **§4.4（b）不做**：破坏宿主边界与导入表闸门，收益 0.1~0.3 s。
5. **§4.6（常开麦）做成设置里的可选项，默认关**，是否要做见 §9。

## 7. 最小验证实验（实施后做；本轮没改代码，没法端到端测）

**E1 确定性单测（离屏）**：`snow-stt` 用 Fake 后端模拟"加载 N s"、脚本化来源模拟"开麦 0.8 s 后才有音频"，断言：①加载期间到达的样本全部进缓冲、加载完成后按顺序喂完；②缓冲满上限（30 s）时丢最旧并发出提示；③STOP 在加载中到达时，等加载完、喂完积压、冲刷后才发 `STOPPED`；④CANCEL 立即退出不喂。判据：全部通过。再加 wav 回归：同一 wav 用旧流程（加载后开始）与新流程（人为延迟加载 5 s）识别，FINAL 文本一致。

**E2 端到端计时（需要真人对着麦克风，无法无人值守，声学回环被回声消除滤掉，见 `snow-stt-worker.md`）**：在 host、UI `main`、worker 开麦首包、模型就绪、积压喂完各打点（同一 QPC 时钟）。三个条件各 5~10 轮：UI 冷拉起（页缓存热）、UI 冷拉起（清页缓存，沿用 §12.1 的做法）、UI 已存在。人工办法：按键后立刻以约 1 次/秒的节奏报数"一二三四五…"，数识别结果里第一个出现的数字。判据（建议）：
  - 热页缓存：按键到首个麦克风包的中位数 ≤ 1.3 s，p95 ≤ 1.8 s；
  - 冷页缓存：中位数 ≤ 1.6 s；
  - 报数的第一个被识别的数字 ≤ "二"（约 1.2~2 s）；
  - 追赶耗时（模型就绪到积压喂完）≤ 积压时长 × 0.25；
  - 按住说话：在"在录"之后松开 0.5 s 内的短句，文字完整出现，不再被丢弃。

**E3 内存与退出**：听写结束后 UI 与 worker 在 3 s 内全部消失，宿主私有提交保持 ≤ 2.2MB（与 `idle` 场景同口径，`scripts/verify-tray-host-split.ps1`）；加载期间 worker 多出的缓冲 ≤ 2MB。

**E4 麦克风打开耗时的机器差异**：用 `<scratchpad>/audioprobe` 的思路在另一台机器、另一个默认麦（USB、蓝牙、笔记本阵列）各测 3 次。判据：0.7~0.9 s 是否普遍；若别处只有 100~200 ms，则"零丢失"的现实差距更小，反过来如果蓝牙耳机经常 > 2 s，需要在 UI 提示里区分"麦克风在打开"。

**E5（可选，不影响主线）加载提速**：量 sherpa/ORT 会话创建是否能靠预优化模型缩短（ORT 的优化后模型落盘），以及单线程加载与 `threads` 的关系。目前没有数据，不当作结论。

## 8. 对 `tray-host-split.md` §10 第 4 条的修订建议

当前文字（已改判）末尾写："代价是冷拉起时按住说话的开头可能丢约 1s，接受（后续可能另做 worker 预拉优化，不在本条范围）"。建议改成：

> **代价与配套**：冷拉起 UI 时，按键到麦克风可用的这段（现行 worker 为 UI 冷启动 + worker 启动 + 模型加载 + 麦克风打开，本机实测 4.5~15 s，其中模型加载占大头，**与 UI 是否常驻基本无关**）里说的话会丢。配套工作（见 `research/dictation-cold-start.md`）：①worker 先开麦、环形缓存、模型就绪后追赶，丢字窗口降到约 1.0~1.4 s（其中麦克风打开 0.7~0.9 s 是硬件下限）；②UI 带 `--hint dictation` 启动时在 `main` 最早处并行拉 worker；③宿主直接拉 worker、宿主自录音不做。语音**进行中**仍保活（`dictation` 状态型原因）。

§5 表格"语音转文字进行中"一行里"冷启动延迟问题见 §10 问题 4"、§6 的启动预算也可顺手补一句"听写命令不在首帧路径上，不受 0.9 s 验收线约束"。

## 9. 需要用户决定的点

1. **是否接受"麦克风打开的 0.7~0.9 s 内说的话仍会丢"**：这是所有方案的下限。接受 → 做 §4.1 + §4.3 即可；不接受 → 只有"麦克风常开"（§4.6）一条路，要不要做成设置里的可选项。
2. **UI 起来前由谁拉 worker**：推荐"UI `main` 早拉"（§4.3，宿主零增量）；若要再省 0.06~0.15 s 愿意承担句柄交接与孤儿清理，才做"宿主直接拉"（§4.2）。
3. **按住说话"在录之后松开"的语义**：推荐松开 = 等加载与积压喂完后正常出字，而不是现在的整段丢弃。这是行为变化，需要确认。
4. **字晚出来的提示**：模型加载 4~14 s 内浮窗/托盘显示"录音中，识别稍后"。键入模式下文字会在加载完后一口气打出来，是否可接受。
5. **默认双语模型 x-asr 480ms 的加载偏慢**（本机现测 5.7~13.6 s，历史 2.5 s）：是否值得在"加载时长"上单独立项（换默认、预优化模型），不在本文范围。
6. 缓冲上限（建议 30 s，超出丢最旧并提示）与 `max_seconds`（默认 120 s）怎么配合。

## 10. 未证实项

1. **worker 里 `snow-audio-recorder` 的开麦耗时**：探针量的是裸 WASAPI；worker 里的真实耗时与首包时刻没有单独量，只从 START→PONG 与 wav 口径的差（约 0.4 s，噪声大）推断同量级。
2. **UI 冷拉起到"可以处理听写命令"**：由 §12.1 的分段数据推算（热 ≈ 0.28 s、冷 ≈ 0.45 s），没有对听写命令实测；split 默认后 UI 引导是否有变化也没重测。
3. **按键到"麦在录"的端到端数字**（§4.7 表）全是公式估算，等 E2。
4. **模型加载为什么比历史慢 2 倍**：推测是后台负载与第一次读盘；没控制变量（没关其它进程，没清页缓存），不能当作稳定结论。换机器、空闲负载下的加载时间未知。
5. **麦克风打开时间的机器差异**（E4）：只在这一台 Realtek Jack Mic 上测，首次 1.3~1.5 s 的离群原因未查。
6. **积压追赶期间 RTF**：用的是实时流的 RTF 数据；快进喂入时 CPU 满载与实时喂入的差异、与其它进程的争用没测。
7. **离线 / VAD 模式下积压喂入 VAD 的行为**未验证。
8. **系统语音后端**（自己占麦克风，不能喂 PCM）这条不适用，其冷启动延迟（`SpeechRecognizer` 创建与首包）没测，本机联机语音开关关闭。
9. **扩展点缓解与 WASAPI 共存**只在探针里短时测过（采集 2 s）；长时间运行与设备热插拔没测。
10. 业界部分：Alexa 500 ms 预录数字、Win+H 的"等 Listening"说法都没读到一手文档；LocalYapper 内容来自镜像页面摘要。
